#+TITLE: Build Simplification
#+STARTUP: overview

* Vision

Make ~swift build~ the primary tool for everything that doesn't need an
~.app~ bundle, and reduce ~xcodebuild~ / ~project.pbxproj~ to the bare
minimum required to ship a signed, sandboxed AppKit application. Every
piece of code should live in an SPM package or be generated by a script
from a flat manifest — no Xcode-UI-only state.

Done so far: 91 extension dylibs → single SPM static library; LuaSkin →
SPM; per-extension Xcode targets removed (96 → 3); hs CLI → SPM; Lua
file copying → manifest-driven; script sandboxing enabled; ~-undefined
dynamic_lookup~ removed; pbxproj cut ~80 %.

* Generator automation

** NOT FEASIBLE Make ~generate-hsextensions.sh~ a build-time phase
   :LOGBOOK:
   - State "NOT FEASIBLE" from "TODO"       [2026-05-11]
   :END:
   Not feasible. The generator outputs (~HSExtensions.m~,
   ~HSExtensions+Preload.h~) are sources inside the ~HSExtensions~ SPM
   package. SPM resolves and compiles its packages *before* Xcode
   target build phases execute. A Run Script phase in the Hammerspoon
   target would run too late — SPM has already compiled the (potentially
   stale) generated files. Moving the generator earlier is not possible
   without SPM build-tool plugins, which cannot run arbitrary shell
   scripts against the host filesystem.

** NOT FEASIBLE Make ~generate-lua-files-xcfilelists.sh~ a build-time phase
   :LOGBOOK:
   - State "NOT FEASIBLE" from "TODO"       [2026-05-11]
   :END:
   Not feasible for a related reason. The outputs (~lua-files.inputs.xcfilelist~,
   ~lua-files.outputs.xcfilelist~) are xcfilelists consumed by Xcode's
   dependency system to decide whether the "Copy Extension Lua files"
   phase needs to run. They must exist and be correct *before* the
   build starts — a Run Script phase cannot update them in time for the
   same build invocation to use the new values.

   :LOGBOOK:
   - State "DONE" from "TODO"               [2026-05-11]
   :END:

* Manifest unification

** RESEARCHED Unify ~extensions.list~ and ~lua-files.list~ into one manifest
   Investigated both manifests and both generator scripts thoroughly.

   Current state:
   - ~extensions.list~: 92 ~luaopen_*~ symbols (one per line), drives
     ~generate-hsextensions.sh~ which emits 3 C/ObjC files.
   - ~lua-files.list~: 110 file paths (1 luaskin.lua + 109 extension .lua),
     drives ~generate-lua-files-xcfilelists.sh~ which emits 2 xcfilelists.

   Relationship mapping (NOT 1:1):
   - 24 extensions are Lua-only (no C entry point): ~_coresetup~, ~alert~,
     ~appfinder~, ~applescript~, ~deezer~, ~expose~, ~fnutils~, ~geometry~,
     ~grid~, ~inspect~, ~itunes~, ~javascript~, ~layout~, ~logger~,
     ~messages~, ~mjomatic~, ~redshift~, ~spoons~, ~spotify~, ~tabs~,
     ~tangent~, ~utf8~, ~vox~, ~watchable~. These appear in ~lua-files.list~
     but not ~extensions.list~.
   - 1 entry (~luaskin.lua~) is not an extension at all — it comes from
     ~Packages/LuaSkin/~.
   - Several extensions have multiple Lua files: ~window~ (6), ~network~ (5),
     ~httpserver~ (3), ~webview~ (2), ~location~ (2), ~drawing~ (3),
     ~doc~ (2), ~canvas~ (2).
   - Some C symbols don't map cleanly to directory names: ~luaopen_hs_liblsqlite3~
     lives under ~sqlite3/~, ~network~ has 4 separate C entry points
     (~networkconfiguration~, ~networkhost~, ~networkping~, ~networkreachability~)
     but the umbrella ~network.lua~ has no C counterpart.

   Proposed unified format (TSV):
   #+BEGIN_EXAMPLE
   # extension-dir  entry-points (comma-sep, optional)  lua-files (comma-sep)
   _coresetup       -                                   _coresetup.lua
   application      luaopen_hs_libapplication,luaopen_hs_libapplicationwatcher  application.lua
   network          luaopen_hs_libnetworkconfiguration,luaopen_hs_libnetworkhost,...  network.lua,network_configuration.lua,...
   sqlite3          luaopen_hs_liblsqlite3              sqlite3.lua
   #+END_EXAMPLE

   Migration steps:
   1. Create ~extensions.tsv~ (or ~extensions.manifest~) from the two lists.
   2. Update ~generate-hsextensions.sh~ to parse column 2 (skip ~-~ rows).
   3. Update ~generate-lua-files-xcfilelists.sh~ to parse column 3, resolving
      paths via column 1 as directory prefix.
   4. Handle the ~luaskin.lua~ special case (either a magic row or separate).
   5. Delete the two old manifests.

   Risks:
   - TSV is fragile with commas in filenames (unlikely here but unpleasant).
     YAML would be cleaner but adds a parser dependency to the bash scripts.
   - The directory-convention alternative (auto-discover ~.lua~ files in each
     extension dir) is simpler but would break the explicit "this is what gets
     bundled" contract and make the xcfilelist generation non-deterministic
     without sorting.

   Effort: medium (half-day). Benefit: low-medium (removes sync risk between
   two files, but the files change rarely). Recommendation: defer until
   generators are automated build phases (those TODOs above), then unify.

   - MJConsoleWindowController: 2 IBOutlets + 1 IBAction
   - MJPreferencesWindowController: 4 IBOutlets + 5 IBActions

   - Slight increase in code volume (~200 lines of programmatic UI code).

   Effort: medium (half-day for all 3). Benefit: low. The XIBs are not

   app-level singletons regardless. Recommendation: skip. The effort-to-benefit
   ratio is poor and the XIBs are stable, rarely-changed artifacts.

** RESEARCHED Explore making ~BuildDocs~ a build-time SPM dependency
   Read ~scripts/docs/Package.swift~ and investigated SPM plugin options.

   Current state: BuildDocs is a standalone SPM executable target (~2114
   lines across 8 Swift files) with one dependency (~swift-argument-parser~).
   It parses ~///~ (ObjC) and ~---~ (Lua) doc comments from the entire
   source tree and writes JSON/Markdown/HTML/SQL outputs. It is built
   out-of-band and invoked by a Run Script build phase.

   *Option A: SPM Build Tool Plugin (~.plugin(capability: .buildTool(...))~)*
   - Build tool plugins run in a strict sandbox: read-only access to the
     package source directory, write access only to a designated output
     directory (~$DERIVED_DATA/...~), no network access.
   - BuildDocs needs to walk the entire repo source tree (~extensions/~,
     ~Hammerspoon/~, etc.) which may or may not be within the plugin's
     input scope depending on which package hosts the plugin.
   - BuildDocs writes output files (docs.json, html, etc.) to configurable
     paths — the sandbox restricts this to the plugin output directory only.
   - Build tool plugins must declare their outputs statically; BuildDocs
     generates a variable number of per-module HTML/Markdown files, making
     static output declaration impractical.
   - *Verdict: not feasible* without significant rearchitecting of BuildDocs.

   *Option B: Command Plugin (~.plugin(capability: .command(...))~)*
   - Command plugins are invoked manually (~swift package generate-docs~),
     not automatically during build. This doesn't solve the "automatic
     generation" goal.

   *Option C: ~.executableTarget~ in the workspace, invoked by Run Script*
   - Add BuildDocs as a package dependency of the workspace (not a target
     dependency of the app). The Run Script phase invokes the built binary.
   - Advantage: ~swift build~ compiles BuildDocs alongside the app, ensuring
     it's always up to date. The "tool missing" skip logic goes away.
   - Disadvantage: adds ~swift-argument-parser~ as a workspace dependency
     (pulled into Xcode's package resolution). BuildDocs compilation adds
     ~5-10s to clean builds.
   - This is the most practical option but the benefit is marginal: the
     current out-of-band build works fine and the Run Script phase already
     handles the "not compiled" case gracefully.

   Effort: low-medium for Option C (2-3 hours). Benefit: low (removes a
   manual build step that rarely matters). Recommendation: defer. The
   current setup works. If the "Compile docs.json" build phase gets proper
   input/output file lists (separate TODO), that addresses the main pain
   point without restructuring BuildDocs.

** RESEARCHED Evaluate ~HSExtensions/Package.swift~ source-path maintenance
   Investigated whether removing the explicit ~sources:~ array from
   ~Package.swift~ would allow SPM auto-discovery to compile everything
   correctly.

   Current state: 145 source paths hand-listed in ~extensionSourcePaths~.
   SPM auto-discovery (following symlinks) finds 138 compilable files
   excluding the ~Hammerspoon/~ symlink.

   Blockers for removing ~sources:~:
   1. *Hammerspoon symlink*: exists for ~.headerSearchPath("Hammerspoon")~.
      SPM auto-discovery would compile all 19 app-target ~.m~ files →
      duplicate symbols. Excluding ~"Hammerspoon"~ removes header access.
   2. *ipc/cli/hs.m*: visible through ~ipc~ symlink, must not be compiled
      (built by its own SPM package). Needs ~exclude: ["ipc/cli"]~.
   3. *sqlite3/lsqlite3.c*: ~#include~'d by ~lsqlite3_wrapper.m~. SPM
      auto-discovery would also compile it as plain C → duplicates. Needs
      ~exclude: ["sqlite3/lsqlite3.c"]~.

   Feasible with 3 ~exclude:~ entries + an explicit
   ~.headerSearchPath("../../../../Hammerspoon")~ replacing the symlink.
   Package.swift drops from 246 → ~100 lines. New extensions no longer
   need a ~Package.swift~ edit.

   Effort: low (1-2 hours). Benefit: medium (eliminates 145-line source
   list, simplifies "add extension" workflow). Recommendation: do.
