#+TITLE: Build Simplification
#+STARTUP: overview

* Vision

Make ~swift build~ the primary tool for everything that doesn't need an
~.app~ bundle, and reduce ~xcodebuild~ / ~project.pbxproj~ to the bare
minimum required to ship a signed, sandboxed AppKit application. Every
piece of code should live in an SPM package or be generated by a script
from a flat manifest — no Xcode-UI-only state.

Done so far: 91 extension dylibs → single SPM static library; LuaSkin →
SPM; per-extension Xcode targets removed (96 → 3); hs CLI → SPM; Lua
file copying → manifest-driven; script sandboxing enabled; ~-undefined
dynamic_lookup~ removed; pbxproj cut ~80 %.

* Generator automation

** TODO Make ~generate-hsextensions.sh~ a build-time phase
   Currently must be run manually after editing ~extensions.list~.
   Move it into a Run Script phase with ~extensions.list~ as input
   and the three generated files as outputs. Xcode skips the phase

** TODO Make ~generate-lua-files-xcfilelists.sh~ a build-time phase
   Same story — must be run manually after editing ~lua-files.list~.
   Declare the manifest as input and the two xcfilelists as outputs.

* Manifest unification

** TODO Unify ~extensions.list~ and ~lua-files.list~ into one manifest
   The two manifests partially overlap (one extension = one symbol +
   one-or-more Lua files). A single per-extension manifest (YAML, TSV,
   or structured text) could drive both generators and eliminate the
   sync risk. Larger refactor — do after the generators are automated.

* Xcode surface reduction

** TODO Audit ~Hammerspoon/~ sources for SPM migration candidates
   ~Info.plist~, entitlements, ~.xib~ files, the asset catalog, code
   signing, and app-bundle layout must stay in Xcode. Everything else
   is a candidate. ~12 utility files (MJAutoLaunch, MJAccessibilityUtils,
   MJConfigUtils, MJFileUtils, MJVersionUtils, HSLogger, HSAppleScript,
   etc.) could become an SPM "HammerspoonCore" package — but they are
   small, stable, and tightly coupled to the app delegate, so ROI is
   low today.

** TODO Extract app utilities into SPM ~HammerspoonCore~ package
   If the audit above shows enough payoff: move ~MJAutoLaunch~,
   ~MJAccessibilityUtils~, ~MJConfigUtils~, ~MJFileUtils~,
   ~MJVersionUtils~, ~HSLogger~, ~HSAppleScript~ into a new SPM
   package consumed by the app target. Reduces Xcode-compiled source
   count and makes the utilities independently testable.

   In ~project.pbxproj~ the phase UUID (4FF7395127344D370007074E) is

* Speculative / future

** TODO Explore replacing ~.xib~ files with programmatic UI
   Three XIBs (~MainMenu~, ~ConsoleWindow~, ~PreferencesWindow~) are
   the main reason UI controllers must live in the Xcode target. If
   rewritten as programmatic ~NSWindow~/~NSMenu~ setup, the
   controllers could move to SPM and the Xcode target shrinks to
   ~MJAppDelegate~ + ~MJLua~ + resources.

** TODO Explore making ~BuildDocs~ a build-time SPM dependency
   Currently a separate SPM project under ~scripts/docs/~, built
   out-of-band. If wired as a ~.plugin~ or build-tool dependency of
   the main workspace, doc generation becomes automatic and the
   conditional skip logic in the build phase goes away.

** TODO Explore enabling more compiler warnings
   ~Project-Base.xcconfig~ has 12 commented-out warnings (~GCC_WARN_SHADOW~,
   ~CLANG_WARN_IMPLICIT_SIGN_CONVERSION~, etc.). Each should be tried,
   and the ones that pass (or can be fixed) should be enabled to raise
   the baseline code quality.

** TODO Explore ~GCC_OPTIMIZATION_LEVEL~ per-configuration
   Currently ~0~ project-wide (even Release/Profile). Release builds
   should probably use ~s~ or ~2~. Requires verifying Lua runtime
   correctness under optimization.

** TODO Explore removing the precompiled header
   ~Hammerspoon-Prefix.pch~ only imports ~<Cocoa/Cocoa.h>~ and defines
   ~LUA_USE_MACOSX~. With modules enabled (~CLANG_ENABLE_MODULES = YES~)
   the PCH adds little value and is one more Xcode-only artifact.

** TODO Evaluate ~HSExtensions/Package.swift~ source-path maintenance
   The 246-line package manifest hand-lists every ~.m~/~.c~ file. If
   SPM's directory-based source discovery could be leveraged (by
   reorganising the symlink tree), the explicit list becomes
   unnecessary and adding an extension no longer requires editing
   ~Package.swift~.
